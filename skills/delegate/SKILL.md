# Делегирование работы внешним моделям

Три модели других вендоров работают через подписки владельца. Смысл - снимать
с себя объём и рутину, а не перекладывать ответственность: итог перед владельцем всё равно
твой.

## Инициатива: где молчать, а где спросить

Решение владельца: **мелочь делаю молча, на крупном спрашиваю.** Граница проходит по
времени ожидания и по риску для файлов, а не по важности задачи.

**Молча** - вызов только на чтение, который уложится примерно в минуту: любой Flash,
Terra, Luna. Это большинство делегирований. В конце ответа одной строкой скажи, кого
звал и что проверил, - чтобы выбор был виден, но не требовал внимания.

**Сначала спроси** - и назови ожидаемое время:
- Grok на `high` или `xhigh` - он думает минутами, у 4.6 было 43 секунды только до первого токена;
- Sol на `max`;
- консилиум из двух-трёх моделей;
- **любой вызов с `-w`** - правки в файлах владельца делегируем только с его ведома.

Формат вопроса короткий: что хочу отдать, кому, сколько ждать. Не расписывай обоснование
на абзац - владельцу нужно решить за секунду.

## Когда делегировать

Хорошие кандидаты - работа, где **много однотипного** и **результат легко проверить**:

- перелопатить десятки файлов и выписать из них что-то по образцу;
- одинаковая правка по всему проекту;
- рефакторинг с понятным критерием готовности;
- широкий ресёрч, где надо прочитать много и сжать;
- черновик текста по нашим правилам.

**Не делегируй:**

- то, где нужен контекст нашей истории - модель его не видит и выдумает;
- работу через твои собственные предметные скиллы, завязанные на внутренние конвенции,
  сетевые диски и формулы в таблицах: внешняя модель их сломает;
- всё, что уходит наружу: письма, сообщения, коммиты, деплой;
- мелочь, которую сам сделаешь за минуту. Каждый вызов - от 10 секунд до нескольких минут.

**Наружу не отдавай:** внутренние документы с коммерческими данными (закупочные цены,
маржа), доступы и ключи, персональные данные людей. Материалы уходят на серверы чужого
вендора. Пути, которые нельзя читать даже случайно, закрывай на уровне ядра - см.
переменную `ASK_SECRETS_FILE` в README.

## Кому какую работу

Выбирай по **вектору задачи**, а внутри вектора - по весу. Единой лестницы «лёгкий →
средний → тяжёлый» поперёк всех задач нет: лучший лёгкий исполнитель на разборе файлов
и на правке кода - разные модели.

| Вектор | Лёгкий · молча | Средний · молча | Тяжёлый · спросить |
|---|---|---|---|
| Разобрать объём файлов, извлечь по образцу | Gemini `-e low` | Gemini (дефолт) | Gemini `-m gemini-3.1-pro-high` или Grok `-e high` |
| Мелкая механика, короткий контекст | Codex `-m gpt-6-luna -e low` | Codex `-m gpt-6-luna -e medium` | - |
| Ресёрч в вебе | Gemini `-e medium` | Grok (дефолт) | Grok `-e high` |
| Свежее из X, что было недавно | Grok (дефолт) | - | - |
| Правка и рефакторинг кода | Codex `-e medium -w` | Codex `-e high -w` | - |
| Ревью кода, поиск дыр в логике | Codex `-e medium` | Codex `-e high` | Codex `-m gpt-6-astra -e xhigh` + консилиум |
| Архитектура, спорное решение | - | Codex `-m gpt-6-astra -e high` | Astra и Grok вдвоём |
| Терминал, computer use, миграции | - | Codex `-m gpt-6-astra -e high` | Astra `-e xhigh` |
| Аккуратная правка в чужом сложном коде | - | Gemini `-m claude-sonnet-4-6 -w` | - |
| Юридические и документные задачи | - | Grok (дефолт) | Grok `-e high` |
| Текст по твоим правилам | Gemini `-e low -s СКИЛЛ` | Gemini `-s СКИЛЛ` | - |
| Математика, STEM | Gemini `-m gpt-oss-120b-medium` | - | - |
| Картинки, раскадровки, видео | Grok `-w` | - | - |

Три вещи, без которых матрица врёт:

- **Усилие двигает сильнее, чем модель.** Gemini Flash идёт 51 → 53 → 56 от `low` к
  `high`, Luna - 34 → 39 → 52. Прежде чем менять исполнителя, подними `-e`: это дешевле
  и почти всегда быстрее.
- **Luna - только до ~250К токенов контекста.** Дальше её удержание падает до 41%, и она
  начинает выдумывать. На тесте из 36 файлов (~100К токенов) она дала 12 из 12 верно; на
  папке впятеро больше доверять ей нельзя.
- **Grok - там, где ждать не жалко.** Он умнее всех (61), но 43 секунды только до первого
  токена. В интерактивном цикле он худший выбор, в фоновой проверке - лучший.

Одна работа - одна модель. Раздавать одно и то же двоим есть смысл только для мнения
(это скилл `second-opinion`), а не для работы: получишь две расходящиеся версии файлов.

**Не делегируй ради качества кода.** На SWE-bench Pro впереди модели Claude (Fable 5 -
80,3%), а не эти трое (Sol - 64,6%). Делегирование выигрывает объёмом, скоростью и
экономией контекста, а не тем, что напишет лучше тебя. Нужно «правильно с первого
раза» - делай сам.

## Как звать

**На Маке внутри agterm (`AGTERM_ENABLED=1`) — видимый режим, по умолчанию.** Модель
открывается интерактивно в правой панели твоей вкладки, а если там уже кто-то работает —
в новой вкладке рядом. Владелец видит работу и может вмешаться, Claude-посредник токены
не тратит. Задание пиши файлом, итог модель кладёт в файл, готовность — файл не пустой:

```bash
~/.claude/scripts/delegate-tab.sh -c codex|gemini|grok [-m МОДЕЛЬ] [-e УСИЛИЕ] [-w DIR] \
  [-n ПОДПИСЬ] [-p auto|split|tab] [-W СЕК] ЗАДАНИЕ.md
```

Без `-W` скрипт сразу печатает путь к итогу — жди его через Monitor с until-циклом по
файлу. С `-W 600` ждёт сам и печатает итог. Первый запуск Codex в новой папке спросит
доверие — подтверди в той вкладке (`agtermctl session type --target ID` с переводом
строки). **Слово «ГОТОВО» ничего не доказывает:** 25.09 GPT-6 Luna отчиталась без
файла. Верь только файлу.

**Скрытые скрипты** — когда agterm нет (сервер, cron, Telegram) или нужен короткий ответ
без показа:

```bash
~/.claude/scripts/ask-grok.sh   [-e УСИЛИЕ] [-t СЕК] [-d DIR] [-f ПУТЬ]... [-s СКИЛЛ]... [-w] "задача"
~/.claude/scripts/ask-gemini.sh [-e УСИЛИЕ] [-t СЕК] [-d DIR] [-f ПУТЬ]... [-s СКИЛЛ]... [-w] "задача"
~/.claude/scripts/ask-codex.sh  [-e УСИЛИЕ] [-t СЕК] [-d DIR] [-f ПУТЬ]... [-s СКИЛЛ]... [-w] "задача"
```

Субагенты `grok`, `gemini`, `codex` (инструмент Agent) — это Claude Sonnet, который зовёт
скрипт. Работа невидима, и посредник тратит токены Claude. На Маке их не используй,
если открыт agterm; они уместны только там, где видимого режима нет.

## Какая модель отвечает

| | по умолчанию | когда менять `-m` |
|---|---|---|
| **Grok** | `grok-4.7` (дефолт CLI) | быстрая правка кода - `grok-4.7-build-fast` |
| **Codex** | `gpt-6-sol` из `~/.codex/config.toml` | трудное - `gpt-6-astra`; мелочь - `gpt-6-luna` |
| **Gemini** | `gemini-3.8-flash-high` (задан нами явно) | под чистый reasoning - `gemini-3.1-pro-high` |

**Подробный разбор - в `references/models.md` рядом с этим файлом:** независимые замеры
контекста, надёжного объёма и уровней усилия по каждой модели, таблица «работа → кому»
с обоснованием, квоты и слабые места каждой. Читай его, когда выбор неочевиден.

Коротко, что важно помнить. Настоящий 1M контекста из внешних моделей есть только у
Gemini Flash, Codex режет окно до 272K, Grok после 200K стоит вдвое дороже. Самая
сильная внешняя модель - `gpt-6-astra`, она же лучше всех держит длинный контекст.
Gemini 3.8 Flash - лучший баланс скорости и ума. Grok думает дольше всех.

Через agy доступны и чужие модели - `claude-sonnet-4-6` (аккуратная правка в чужом
сложном коде), `gpt-oss-120b-medium` (математика и STEM). **У них отдельная квота от
Gemini**, общий пул не делят.

**Усилие `-e` без нужды не передавай** - тогда действует то, что настроено в самом
инструменте. У Codex это `ultra`, и понижать его молча нельзя: владелец выставил осознанно.
Ставь `-e low` осмысленно, на рутину, где ждать незачем.

## Правки: `-w` и граница `-d`

Без `-w` модель физически не может ничего записать - это проверенная граница, а не
обещание. С `-w` правки разрешены **только внутри `-d`**, за его пределами не пускает
ядро.

**`-w` требует явного `-d` - скрипты откажутся работать без него.** Так сделано
намеренно: раньше рабочим каталогом молча становилась папка первого материала, и просьба
поправить один файл открывала на запись всё дерево проекта. Задавай `-d` ровно той
папкой, которую можно менять, и никогда не указывай `-d ~/Documents`.

Перед делегированием с правками: если папка под git - убедись, что рабочее дерево чистое.
Тогда результат виден одним `git diff`, а откат стоит одну команду.

## Передать наши правила: `-s`

Флаг `-s` подмешивает наш скилл в начало задания и открывает модели его папку - она
дочитает справочные файлы сама. Имя берётся из `~/.claude/skills`, можно несколько:

```bash
~/.claude/scripts/ask-gemini.sh -s writing-style -t 600 "Перепиши текст о компании: ..."
```

Передавай скилл, когда у работы есть твои правила: редакторский стиль, конвенции
именования, чеклисты. Не передавай скиллы, завязанные на сетевые диски и формулы в
таблицах, - такое делай сам.

## Проверка - обязательный шаг

**Отчёт модели о собственной работе ничего не доказывает.** Проверено на живом примере:
Codex отрапортовал, что записал `файл.txt`, а на деле создал `file.txt` латиницей.

Хуже того, **сам инструмент врёт не хуже модели**: у agy есть открытый баг,
где при отклонённом инструменте он возвращает код 0 и статус SUCCESS с пустым результатом,
а настоящая причина уходит в stderr. Поэтому «код возврата 0» ничего не значит - обёртки
проверяют непустоту ответа, но окончательный судья ты.

Доказательство - это **проверяемый след**, а не фраза «я проверил»: дифф, список файлов на
диске, вывод теста, который падал до правки и проходит после. Приняв «я всё сделал» без
следа, ты принял ничего.

После любой работы с `-w`:

1. `git diff` (или чтение файлов, если не git) - что изменилось на самом деле;
2. `ls` каталога - не появилось ли лишних файлов и не перепутаны ли имена;
3. если есть тесты или сборка - прогони.

**Про размер задачи.** Делегирование окупается не всегда: накладные расходы на запуск и
на твою же проверку результата съедают выигрыш на коротких задачах. Практика других
команд: работа короче примерно пятнадцати минут даёт отрицательный итог - быстрее сделать
самому. И узкое место не в модели, а в том, сколько чужой работы ты успеваешь отревьюить.

владельцу показывай итог своей работы: что сделано, что ты проверил, что осталось
непроверенным. Не пересказ чужого отчёта.
